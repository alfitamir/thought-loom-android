# AGENTS.md

## Architecture decisions
- Cloud backup lives in `src/lib/sync.ts`; `src/lib/ideas.ts` stays pure localStorage storage (no supabase imports, no cycles). Why: sync needs local storage access, and the reverse import would create a module cycle.
- The Idea shape has ONE canonical zod schema (`src/lib/idea-schema.ts`, browser-safe: zod + the erased `Idea` type only). The Drive sync route extends it with payload caps; the backup parser (which also reads Drive files) validates field-by-field against it; the Supabase row mapping in `sync.ts` is guarded indirectly — a parity tripwire in the schema module plus `idea-schema.test.ts` fails tsc/the suite if a field is added to the `Idea` type without landing in the schema. Why: three integrity bugs (audit F-3.1, F-3.2, the PR #25/#41-era strip fixes) were the same accident — a field added to two persistence paths and missed in the third, where zod's unknown-key stripping silently deleted it.
- The library blob has a storage safety net inside `src/lib/ideas.ts`: every write goes through one guarded path that mirrors the value to `afkari.ideas.lastGood` only AFTER the main write lands, reports refused writes as typed `StorageWriteError`s (subscribers via `onStorageWriteError`; the root component toasts the first failure of a streak) instead of throwing or vanishing, and `loadIdeas` falls back to the mirror when the main value is corrupt — quarantining both raw strings when neither parses. Why: the whole library plus version histories lives in one ~5 MB-quota localStorage value, so quota exhaustion and corruption must degrade loudly, never destructively.
- Cloud sync resolves with a typed `SyncResult` (never rejects) and records `afkari.lastCloudSync` / `afkari.lastCloudSyncError`; Settings renders both in «حالة النسخ الاحتياطي» alongside the Drive state, pending-deletion counts and a storage-usage gauge. Why: a silently failing primary backup reads as a healthy one for weeks (audit F-6.1) — failure has to be visible where the owner looks.
- Idea backup uses `public.ideas` with immutable original text and optional article title/body plus a revision timestamp; RLS is scoped to `auth.uid()`. Why: originals survive editing and newest editions reconcile across devices.
- Article tools use an isolated editor and browser-safe article helpers. AI work goes through `resolveEngine` (`src/lib/ai-engine.ts`): the user's own Gemini key (stored only in device localStorage, called from the browser in `src/lib/gemini.ts`) is preferred; otherwise the authenticated server route with server-only gateway helpers. Why: the user's own key avoids platform credits, while the platform key never reaches the browser.
- Merge suggestions/merging (`src/lib/merge.ts`) and backup files (`src/lib/backup.ts`) are browser-safe; every AI output passes `isComplete`/`isMergeComplete` before it can replace content. Why: lines must never be silently dropped.
- Voice recording's PRIMARY pipeline is `src/lib/audio-recorder.ts`: it records the microphone itself with MediaRecorder in 60-second segments persisted to IndexedDB, transcribed progressively by AI — continuous until the user presses stop, with no recognition session for Android to kill and no restart beeps (PR #11). The older SpeechRecognition pipeline in `src/lib/voice-recorder.ts` (it reopens recognition sessions after every end or error; only stop/cancel, or a mic permission denied from the start, ends it) survives ONLY as a fallback for devices where MediaRecorder is unavailable. Song mode deliberately refuses that fallback: recognition would turn the singing into text, and a song must stay audio. Why the fallback is kept: it is the only recording path on browsers without MediaRecorder, and dictation there beats no dictation.
- Song mode (`src/lib/songs.ts`) records singing into its OWN voice store (`songVoiceStore()`, DB `afkari-voice-songs`) and keeps the assembled recording in the `songs` store of the `thought-loom-audio` DB. Why: the dictation resume pass transcribes everything in the main voice store, and it must never touch a song. Songs live in their OWN library partition (`partitionIdeas` → `songs`, the `/songs` route) — never in the main library list, groups, counts or search. Song recordings are additionally backed up to Google Drive by `src/lib/song-drive.ts` (below); sync proper carries only the idea (flag, lyrics, duration, Drive file id), via the same field plumbing as topic pins. The ONE deliberate transcription of a song is `src/lib/song-lyrics.ts` (the editor's «استخرج الكلمات من الغنا» button ONLY — lyrics are extracted only when the user asks; there is no automatic post-save pass): it fills the lyrics (`text`) with the words as sung via the song prompt in the shared transcription transport, and never overwrites existing lyrics without explicit confirmation. A song file leaves the app only as MP3 (`src/lib/song-export.ts`: WebAudio decode → lamejs encode, cached in the `song-exports` store under a source fingerprint) — the share/download file and the Drive copy alike — because WhatsApp refuses the WebM/Opus masters the recorder produces; in-app playback and transcription keep using the master.
- Liked articles (`Idea.liked`/`source`/`sources`) are other people's writing pasted in via the «مقال أعجبني» dialog. Why the hard AI ban: AI must never modify or learn from them — every gate excludes them (needsPolish, unlabeled/classifyBatch, ask/insights corpora, findMerges candidates, improve style samples, editor smart tools hidden), and the only merge path open to them is the manual concatenation dialog (`manual-merge-dialog.tsx`), which carries attribution into the result via `mergeAttributions`.
- Terminal provider denials are stored in owner-readable `public.ai_access_state`, written only by verified server requests. Why: blocked AI work must not restart on reload or reconnect.
- Gemini calls (`src/lib/gemini.ts`) try a fixed list of fast models with low thinking and fall back on rate limit, missing model, overload or a stalled stream; a rejected key stops immediately. Why: `*-flash-latest` aliases can point at slow thinking models, and each model has its own small free quota.
- Google Drive backup goes through the authenticated `/api/drive/sync` server route (`src/lib/drive-sync.server.ts`, Drive connector via gateway), allowed only for the `DRIVE_OWNER_USER_ID` account; merge rules live in browser-safe `src/lib/drive-merge.ts` and the Drive file keeps its own deletion list. Why: the connector reaches the owner's own Drive, so no other signed-in user may touch it, and deletions must not be resurrected across devices.
- Song recording copies live in a regular My Drive folder «أفكاري — الأغاني» (marked with appProperties `afkari: songs-folder`; each file carries `songId`), managed by `src/lib/song-drive.ts` through the authenticated `/api/drive/song-audio` route (`src/lib/drive-song.server.ts`, same connector and owner-only rule). The upload pass adopts an existing file for a song before re-uploading (lost-response safety), the idea's `driveFileId` is stamped through the normal idea write path, other devices download on demand into their local `songs` store, and a failed Drive-file deletion is tombstoned in `afkari.songDriveDeleted` and retried by the next pass. Why a separate route from the JSON sync: recordings are binary and per-song, and the folder must stay visible in the owner's Drive app rather than hidden in appData.
